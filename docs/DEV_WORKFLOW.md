## 0. 一句话

**想法 → 父 issue → grill 出 ADR → 切成薄 issue → triage 贴状态 → 逐片 tdd → 评审 → ship。** 每一步用一个 skill；状态全靠 label + 开关跟踪。

---

## 1. 流水线 + skill

```
想法
 │  to-prd（把对话变成 PRD，作为一个 GitHub issue = 父/epic）
 ▼
父 issue（一句说明 + 北极星/用户案例；不写 spec/文件路径）
 │  （可选）prototype 去风险（状态机/UI 开放问题）
 │  grill-with-docs → CONTEXT.md 术语 + docs/adr/ 决策
 ▼
ADR（不可逆决策，1-3 句）+ CONTEXT 词表，挂回父 issue
 │  设计评审（设计文档同代码评审）
 │  to-issues（切成薄垂直切片子 issue：Parent + What to build + 验收 + Blocked by + AFK/HITL）
 ▼
子切片 issue（一片一个 issue）
 │  triage（贴 category + state 标签；ready-for-agent 发 agent brief）
 ▼
逐片 tdd（红绿重构；Planning 拿用户 approve）；硬 bug→diagnose；重构→improve-codebase-architecture
 │  代码评审 + ship
 ▼
merge commit（不 squash）→ 关子 issue；全完 → 人手动关父
```

**skill 速查**

| skill | 干什么 | 阶段 |
|---|---|---|
| `to-prd` | 对话 → PRD，提交为 GitHub issue（父/epic） | 入口 |
| `grill-with-docs` | 逼问 → 更新 CONTEXT.md + docs/adr/ | 设计 |
| `to-issues` | plan/PRD → 薄垂直切片 issue | 切片 |
| `triage` | issue 走五态状态机、贴标签、发 agent brief | 分流 |
| `tdd` | 逐片红绿重构 | 实现 |
| `diagnose` | 硬 bug / 性能 regression 调查 | 实现 |
| `improve-codebase-architecture` | 找深挖/重构机会（据 CONTEXT + ADR） | 维护 |
| `prototype` | 扔型原型去风险（状态机 / UI 变体） | 设计 |

## 2. 标签制（Matt 纯化 — 全仓只剩 7 个）

> 2026-06-17 拍：**删掉项目原有的 `priority/*` `area/*` `type/*` 等一整套，全仓只留 Matt 的 7 个标签**，按他原样验证。

**2 个 category：**
- `bug` — 坏了。
- `enhancement` — 新功能或改进。

**5 个 state（状态机）：**
- `needs-triage` — maintainer 待评估。
- `needs-info` — 等 reporter 补料。
- `ready-for-agent` — 规格完整，AFK agent 能独立实现并合并。
- `ready-for-human` — 需人：判断题 / 设计决策 / 外部访问 / 手测 / 设计未定。
- `wontfix` — 不做（含已被取代 / out-of-scope / 已过时 / 已完成可关）。

**规则：每个 triaged 工作项恰好带一个 category + 一个 state。** epic/tracker 类（追踪别的 issue 的总台，如 release 清单 / 验证总台 / Epic）**不进工作态、留空**。

## 3. triage（状态机那只手）

把进来的乱 issue 推过状态机，变成「分类清楚 + 状态清楚 + 规格写好」的活。
**每条 triage 发的评论/issue 都必须开头标：** `> *This was generated by AI during triage.*`

**状态流转：** 没标的 → `needs-triage` → `needs-info` / `ready-for-agent` / `ready-for-human` / `wontfix`；`needs-info` 等 reporter 回了再回 `needs-triage`。maintainer 随时可手动覆盖。

**两种模式：**

**A. dashboard（看「该我管的有啥」）：** 查 tracker，按最老优先列三桶 —— 没标的 / `needs-triage` / `needs-info` 且 reporter 有新动静的。给计数 + 一行摘要，maintainer 挑。

**B. triage 某一条（5 步）：**
1. **Gather** — 读全（body/评论/label/reporter/日期）+ 读旧 triage 笔记（别重问）+ 探代码（用 glossary、尊重 ADR）+ 读 `.out-of-scope/` 看有没有撞过的旧驳回。
2. **Recommend** — 给 category + state 建议 + 理由 + 一句代码现状，**等 maintainer 定**。
3. **Reproduce（只 bug）** — grill 前先试复现：成功（带代码路径）/ 失败 / 信息不足（= 强 needs-info 信号）。
4. **Grill（若需细化）** → 跑 `grill-with-docs`。
5. **Apply 结果：**
   - `ready-for-agent` → 发 **agent brief** 评论（见 §4）。
   - `ready-for-human` → 同 brief 结构 + 注明为何不能甩 agent。
   - `needs-info` → 发 triage notes（已确立的 + 还需 @reporter 答的具体问题）。
   - `wontfix`（bug）→ 客气解释 + 关。
   - `wontfix`（enhancement）→ 写进 `.out-of-scope/` + 评论链过去 + 关（见 §5）。

## 4. agent brief（ready-for-agent 的契约）

issue 移到 `ready-for-agent` 时发的一条结构化评论。**它是 AFK agent 工作的权威契约；原 issue body + 讨论只是 context。**

**原则：**
- **durability over precision** —— **不写文件路径、不写行号**（会过时）；写**接口/类型/行为契约**，点名 agent 该找/改的 symbol。
- **behavioral not procedural** —— 写**做什么**不写**怎么改**（agent 自己重新探代码定实现）。
- **完整可测的验收标准** —— 每条独立可验。
- **显式 out-of-scope** —— 防镀金/越界。

**模板：**
```markdown
> *This was generated by AI during triage.*

## Agent Brief

**Category:** bug / enhancement
**Summary:** 一句话

**Current behavior:** 现在怎样（bug=坏的行为；enhancement=现状）
**Desired behavior:** 做完该怎样（说清边界/错误条件）
**Key interfaces:**
- `TypeName` — 改什么、为什么
- `functionName()` — 现返回什么 vs 该返回什么
**Acceptance criteria:**
- [ ] 具体可测 1
- [ ] 具体可测 2
**Out of scope:**
- 不该碰的 / 看似相关其实分开的
```

## 5. out-of-scope 知识库

驳回的 enhancement 记进 `.out-of-scope/`：
- **一个 concept 一个文件**（多个同类请求归一文件），松散小设计文档体，写**为什么驳** + `Prior requests` 列表（#42 #87…）。
- 两个用途：**institutional memory**（关了 issue 理由不丢）+ **去重**（新 issue 撞旧驳回 → 翻出旧决定不重吵）。

## 6. 文档分层 / 规格住在哪

| 东西 | 住哪 | 性质 |
|---|---|---|
| 领域语言（术语） | `CONTEXT.md` | 稳定，词表，零实现 |
| 不可逆决策的「为什么」 | `docs/adr/` | **1-3 句、单决策、稀有**（hard-to-reverse + surprising + real-tradeoff 三条全中才建） |
| 工作单元（父 + 切片） | GitHub issue body | 稳定 spec / 北极星，不放会变的状态 |
| ready-for-agent 的契约 | issue 上的 **agent brief 评论** | durable、behavioral |
| 详细实现设计 | **`/tdd` Planning 现场敲定** | 涌现，不预写 |

**ADR 颗粒度铁律：** 一条 ADR 一个不可逆决策，1-3 句即可；连接性的模型语言进 CONTEXT.md，**别写多 section 大设计书**（大模板会把可逆细节吸进来 = 过度设计）。

## 7. 切片与并行

- **垂直切片（tracer bullet）**：每片穿透所有层、独立可 demo/merge。**禁横切**（先全 schema 再全 UI = 谁也独立不了、并行不起来）。
- **`Blocked by` = 散文约定**：写在子 issue body 里，靠抓 issue 的人读了、看 blocker 关没关、没关就先不开。**GitHub 不强制**。
- **AFK vs HITL**：AFK（agent 独立做完）可甩多 session 真并行；HITL（要人在环）串行在你的注意力上。
- **并行靠切对**：薄 + 独立 + 垂直 + issue 化 → 多 session 各抓不同 issue 并行推。**切得好不好是设计侧的活**，是「能不能并行」的总开关。

---

## 8. 追踪模型（状态怎么知道）

- **父→子归属** = 子 body 一句 `## Parent #N`（cross-ref）。**`to-issues` 不改父 issue。**
- **状态** = **label + 开/关**。看「啥能抓」就查 `ready-for-agent` 桶；看「还剩啥」就 filter open 子 issue。**Matt 不挂进度条。**
- **父 issue「完成」= 人手动关**（子全关后做整体验收再关）；GitHub 不自动关父。
- **可选增强（非 Matt 纯）**：父 body 挂 `- [ ] #N` task-list / native sub-issues 能得进度条 + 自动打勾，但那是 GitHub 功能、Matt 不做，加不加随意。

---

## 9. 贯穿原则

- **只在不可逆处投入设计**：可逆的（接口/schema/逐项实现）做了才知道哪样好，留 `/tdd` 现场长；不可逆的（架构形态/契约/分类）提前钉死进 ADR。「最后责任时刻」：可逆→写码时定，不可逆→别人依赖它之前定。设计时「忽然难受」= 越线信号。
- **handoff ≠ 交接**：同一个你驱动；fresh agent 靠**文档 + 你在场** re-seed。session 边界画在「上下文满/脏」处，不钉死在某步；小功能可一个 session 连做。
- **评审强度跟反悔成本走**：设计（ADR）审狠（反悔贵），代码审正确性。
- **持久件做小做单一**：一条 ADR 一个决策、一个 issue 一个切片；细节交涌现。
