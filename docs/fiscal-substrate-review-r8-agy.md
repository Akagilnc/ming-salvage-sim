# r8 · agy/gemini(v8)

评审意见如下。针对您提出的三个核心问题，逐一进行闭账审查与架构评估：

### 1. Spine 锁得住吗？——「两个不沟通实现者照此写出同一 tick 引擎」达到没？

**结论：已达到 90%，但仍差最后临门一脚。**
若不进行以下 4 处细节规约，两位独立开发者仍会写出有分歧的引擎逻辑：

*   **① Action 成本的生命周期（一次性 vs 持续性）**
    *   **分歧点**：若一个 Action 具有 `duration_months > 1` 且 `Cost > 0`（如“增饷练兵 6 个月”）。开发 A 可能认为 `Cost` 仅在 resolve 发生的那个 tick 扣除一次；开发 B 可能认为在 modifier 存续的 6 个 tick 中，每个 tick 都要扣除 `Cost`。
    *   **补丁规约**：Action 结构体中必须显式定义 `cost_type` 为 `one_time`（仅在 resolve 当期计入 `Σ Cost`）或 `recurring`（在存续期每个 tick 均计入 `Σ Cost` 参与当期 `k` 的计算）。
*   **② Stock 余额的 Modifier 放大漏洞（物理守恒破坏）**
    *   **分歧点**：若某个 Stock（例如 `省库库银` 或 `B.民欠旧赋`）身上挂有 `scale` 类型的 modifier（例如“省库管理效率 +20%”）。当执行 `transfer_to` 向该 Stock 注入 10 两资金时，开发 A 直接修改 `V_base`，会导致最终 `V_final` 凭空增加了 12 两（凭空印钱，破坏物理守恒）；开发 B 试图修改 `V_final` 并反算 `V_base`，逻辑极度臃肿。
    *   **补丁规约**：**所有代表物理银两的 Stock 账本（省库库银、债务 B、赃银/截留 C）一律不允许挂载 `scale` 类型的持久 modifier**。所有的 `scale` 修饰器只能作用于 Flow（如税率、实征率、漂没率）或参数（如定额）。Stock 的变动必须且只能通过纯代数的 `delta` 或 `transfer_to` 发生。
*   **③ `transfer_to` 的 `k` 缩放行为**
    *   **分歧点**：若某 Action 包含 `transfer_to` 效果（如“主动清缴赃银 5 万两”），当 `Cost > 0` 且 `k < 1`（预算不足，行动打折）时，转移的 `amount` 是否要缩放？开发 A 认为 `amount` 缩放为 `amount * k`；开发 B 认为 `transfer_to` 是守恒函数，应当强行划转 5 万两。
    *   **补丁规约**：明确 `transfer_to` 的 `amount` 若来自被缩的 action（`Cost > 0` 且 `k < 1`），其 `amount` 实际执行值必须乘以 `k`，即 `amount_actual = amount * k`，以保持力度縮放的一致性。
*   **④ 赈济（Due_4）不积欠的公式特判**
    *   **分歧点**：§6.5 写的通式为 `NewDebt_i = Due_i - Paid_i`。开发 A 机械套用循环，会导致本月未全额拨付的 `赈济` 产生 `NewDebt_4` 并累加进债务；开发 B 根据 §3 文本描述对 `i=4` 进行了硬编码特判。
    *   **补丁规约**：§6.5 公式中需写明：`NewDebt_i` 的计算仅适用于 `i ∈ {1, 2, 3}`；对于 `i=4`（赈济），`NewDebt_4` 恒等于 0。

### 2. r7 硬伤真闭账了吗？有没有新引入矛盾？

**结论：已闭账。但引入了一个需要向 LLM/玩家明确的「行政挂空挡」设计。**

*   **省内可支总公式**：**已闭账**。`省内可支 = 省库库银_post + 省内池 + 拨付net + 清欠入库 + 追赃入库` 定义清晰，将所有 Flow 级和 Stock 级可用资金统一，无漏抄。
*   **transfer_to 守恒/loss_sink**：**已闭账**。三方守恒公式（`source`减 = `target`增 + `loss_sink`增）彻底杜绝了黑洞和凭空产钱。
*   **⓪ 时序**：**已闭账**。清零 -> 衰减 -> 新 Action -> 算 k -> 扣库银的顺序完全钉死，消除了时序漏洞。
*   **离散 set**：**已闭账**。但补充一点：对于持续多 tick 且有 `recurring` 成本的 action，其离散 set 是在每个 tick 根据当期 `k` 动态决定是否生效。
*   **B_i 偿还**：**已闭账**。
    *   *数学冗余说明*：在严格优先级付款下，若 `S > 0`（有余银偿债），则本月所有的当前应付 `Due_i` 必然已全额付清（`Paid_i = Due_i`）。因此 `NewDebt_i` 必然为 0。公式 `Repaid_i = min(S, B_i,old + NewDebt_i)` 中的 `NewDebt_i` 在实际运行中恒为 0。这并非矛盾，只是数学冗余，建议保留以兼容未来可能引入的“手动非严格 waterfall 偿债”机制。
*   **⚠️ 新引入的系统级矛盾：火耗与行政费用的“挂空挡”**
    *   **机制**：`火耗实收` 征收后流入了 `C.地方截留/中饱`。它**不自动进入** `省内可支`（Flow）。但省级的行政支出 `官俸/行政`（Priority 2）是从 `省内可支` 中扣除的。
    *   **后果**：如果引擎中没有自动将 `C.地方截留` 转化为 `省内可支` 的机制，那么即使地方火耗征收极多，省级财政依然会因为 `省内池`（正税实征 - 起运）被起运榨干而疯狂积欠 `官俸欠`。
    *   **判决**：这极其真实地模拟了明末“官绅脑满肠肥（地方截留多），官衙无米下锅（俸饷积欠）”的病态。这属于**符合历史的设计**而非 Bug。但必须在实现规约中声明：**必须通过特定 Action（如“平水拨用”、“挪借火耗”）将 C.地方截留 通过 `transfer_to` 转入省库，才能用于支付俸饷**。

### 3. 还有没有逼回来改架构的隐藏问题？

**结论：没有。**

*   **乘法 modifier 的“一票否决”效应**：`∏ max(0, 1 + scale_i)` 意味着如果存在一个 `scale = -1`（-100% 灾荒），该项乘积直接归零，任何正向修饰器均失效。这是预期的策略硬核设定，不属于架构缺陷。
*   **“起运优先”导致的省库瞬间归零**：`起运池 = min(实征, 定额)` 意味着在崇祯朝高压起运下，只要实征不足定额，省内留存（`省内池`）就绝对为 0。全省行政完全依赖北京 `拨付net` 吊命。这完全符合明末陕西历史事实，无需修改架构。

### 最终判决

**Spine 可锁，锁死上述 4 处细节后，可开写引擎。**
