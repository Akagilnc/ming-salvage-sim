# 一、 §0.1 守恒断言完整性与口径评审 (v12 草表)

### 1. CASH_out 存在“行政成本类”流出的漏算 (G3 已暴露)
在草表主断言中：
```
CASH_out = 起运到京 + Σ实付(军饷/官俸/宗禄/赈济) + Σ偿旧欠 + Σ补饷支付
```
*   **口径漏洞**：像 `清丈` 这种“行政成本类” action，其产生的实际成本 `ec` (即 `cost * k`) 会直接从 `省库库银` 中扣除（`cash['省库库银'] -= ec`）。但它既不属于 `起运到京`、也不属于 `实付` 或 `偿旧欠`。如果在公式中只列出 `Σ补饷支付`，在语义上属于张冠李戴，若不归入则会导致大账不平。
*   **修正建议**：将 `CASH_out` 中的 `Σ补饷支付` 泛化为更通用的 `Σaction实际支付 + Σaction行政成本`（或统称为 `Σaction现金流出`）：
    $$\text{CASH\_out} = \text{起运到京} + \sum\text{实付} + \sum\text{偿旧欠} + \sum\text{action实际支付} + \sum\text{action行政成本}$$

### 2. 挪借 / 追赃归 CASH 内部转移的口径是否正确？
*   **完全正确**。因为 `C_地方截留` 等灰账账户本来就在 `CASH` 账户定义中（`CASH = 省库 + C_地方截留 + ...`）。挪借和追赃（`C_中饱/C_地方截留 -> 省库`）只改变了 `CASH` 内部子账户的分布，`ΣCASH` 的总额并没有发生任何跨边界变化，因此不计入边界流是完全正确的。
*   同理，`漂没`（实征的一部分留在 `C_漂没`）和 `中饱`（拨付gross的一半留在 `C_中饱`）也均被扣留在 `CASH` 内部，因此 `CASH_in` 分别以 `实征` 和 `拨付gross` 计入，且不增加对应的 `CASH_out`。这在数学上完全闭合。

### 3. 激活 `efficiency < 1` 后的隐藏边界流雷区
如果未来激活 `efficiency < 1`，它产生的 `C_eff损耗` 也定义在 `CASH` 内：
*   当省库 nominal 支付了 10 万饷，但由于效率只有 0.9，受款方实际只收到 9 万，1 万流向 `C_eff损耗`（CASH 内）。
*   此时，真实的跨边界现金流出 `CASH_out` 只有 9 万，而省库减少了 10 万（其中 1 万转移到了 `C_eff损耗`）。
*   如果引擎在计算 `CASH_out` 时直接按 nominal 的 10 万算，就会导致 `ΔCASH` （仅减少 9 万）与 `CASH_in - CASH_out`（减少 10 万）对不上，从而**破坏守恒断言**！
*   **规则补充**：必须在公式中明确：**当存在支付效率损耗时，`CASH_out` 只计入实际到达边界的金额（`nominal * efficiency`），其余部分作为内部转移进入 `C_eff损耗`**。

# 二、 Spike G1–G7 有没有假 PASS？(Spike 代码)

### 1. G3 存在严重“假 PASS”——断言漏洞掩盖了账目不平
*   **代码 typo**：在 `spike_settle_tick.py` 的第 41 行（`清丈` 逻辑内）：
    ```python
    if ec > 0: cash['省库库银'] -= ec; cash_out += ec; rec['补饷支付']
    ```
    最后的 `rec['补饷支付']` 只是一个表达式求值，**没有执行 `+= ec`**！这导致明细账记录中 `rec['补饷支付']` 最终为 0。
*   **假 PASS 原因**：测试之所以 PASS，是因为现金守恒断言使用的是动态累加的 `cash_out` 变量（它正确地加上了 `ec`），而**没有用明细账 `rec` 账户进行二次校验**。
*   **防假 PASS 改进**：必须加上明细账核对断言，确保宏观流量等于各细分项之和：
    ```python
    assert abs(cash_out - (rec['起运到京'] + rec['实付'] + rec['偿旧欠'] + rec['补饷支付'] + rec['行政成本'])) < EPS
    ```
    一旦加入此断言，G3 将**立刻 FAIL**。

### 2. G3 清丈税基修改未被公式真正覆盖
*   G3 中清丈动作将 `隐田` 挖出 300 转化为 `官民田`（3050 $\rightarrow$ 3350），但因为 `p` 中传入了硬编码的 `'正赋应征': 60`，导致 `正赋 = 60` 依然被使用，未走通 `官民田 * 正赋亩额` 的动态计算路径。
*   这导致“税基变化对应征数额的影响逻辑”在此 spike 中实际上被硬编码跳过了，未能测出动态税基计算下是否会破坏守恒。

### 3. 尚未激活的“藏雷”路径分析
*   **雷点 A：多 Action 静态 k-scaling 的“预算残留”问题**。目前 `k` 是在 ⓪ 阶段根据所有 Action 的预算总和 `ΣCost` 和 `Stock_start` 静态算出的。如果某个支付类 Action（如补饷）因为 `clamp`（比如欠饷已还清）实际上没有花完分配给它的 `ec`，那么这部分钱就会剩在省库中。在目前的实现中，这部分钱直接流向了后面的步骤（变成了 `省内可支`），但这是否符合设计意图？如果本意是“这笔预算被行政锁死，未花完也不能挪作他用”，那这就属于逻辑偏差。
*   **雷点 B：`recurring cost` 的跨 tick 生命周期管理**。如果一个 Action 产生了持续性的每 tick 成本（例如雇佣兵饷），它的生命周期、在省库耗尽（`k < 1`）时的衰减逻辑、以及当省库重新有钱时的恢复逻辑，在目前的设计中完全空白。这很容易在实现跨 tick 时导致修饰符（modifier）和成本的重复扣减或状态丢失。

# 三、 Spine 现在锁得住吗？

**结论：直说，目前依然锁不住。** 如果让两个互不沟通的程序员分别去写，必然会写出两个无法对账的引擎。主要差在以下几步规范的缺失：

### 1. Action 及其修饰符（Modifier）生命周期的状态机规范缺失
*   Modifier 产生的效果（如 `正赋亩额` 增加、`逋赋率` 降低）是“即时生效且只持续本 tick”还是“作为 Buff 挂载在省份上持续 N 个 tick”？如果是持续性的，这些 Modifier 应该存在于省份的哪个数据结构中？每一 tick 结束时如何衰减？
*   当省库银两不足导致 `k < 1` 时，不仅当前 tick 的 `Cost` 要缩水，**其挂载的 Modifier 效果是否也要按比例缩水？**（草表写了“Cost>0 action其 delta/scale/transfer_to.amount 全×k”，但如果该 action 是一个持续性 Buff，后续 tick 中没有 action 实体，只有挂载的 Modifier，这时候怎么乘 `k`？）

### 2. “支付类” Action（如赈济、补饷）与 Due 的关系存在语义冲突
*   Section 3 写道：`1军饷>2官俸>3宗禄>4赈济... 赈济(Due_4=action amount)`。这说明赈济是通过 Due 在步骤 ⑪ 进行 waterfall 支付的。
*   但紧接着又写道：`支付类(补饷/赈济)= 银 Cost 即该笔支付,不再另记 Due`。这又说明赈济是在步骤 ⓪ 作为 Action Cost 直接支付的。
*   **这两种实现方式有本质区别**：如果在 ⓪ 直接支付，它将避开步骤 ⑪ 的 waterfall 优先级约束（变相拥有了比军饷更高的实际支付优先级）；如果通过 Due 支付，它就不应该在 ⓪ 阶段扣除省库。
*   必须二选一，统一口径。

### 3. 跨期与多 Action 冲突的排队/执行顺序未定义
*   在一 tick 内，如果有多个 Action，它们的执行顺序是什么？是并行的（共享同一个初始 `k`），还是串行的（前一个 Action 执行完扣了省库，后一个 Action 的 `k` 基于剩余省库计算）？Spike 采用的是并行计算一个统一的 `k`。这必须在规范中明确。

# 四、 变异测试（Mutation-test）思路建议

为了在 v13/下一轮测试中彻底防止假 PASS，建议在测试框架中引入以下变异测试思路：

1.  **细账核对变异**：故意在引擎扣除省库或增加 C 账户时漏记/多记 0.01 两，看对账系统能否拦截。
2.  **断言覆盖率变异**：自动随机注释掉 `rec` 里的累加逻辑（如故意让 `rec['清欠'] += 0`），如果测试依然 PASS，说明断言存在漏洞。
3.  **零值与边界值变异**：
    *   `Stock_start = 0` 时运行有成本的 Action，检查 `k=0` 时的行为。
    *   `逋赋率 = 1.0`（完全收不上税）或 `0.0`。
    *   `due = 0` 但有 `补饷` Action。
4.  **执行顺序变异**：交换 Action 列表的输入顺序，验证 `k` 的计算和执行结果是否保持幂等（如果不幂等，说明有隐式串行依赖，需定义排队规则）。
