# 召对夜 = 一等容器 + 开放式故事账本；场是软切分；基座为故事服务

Status: Proposed（2026-07-02 #470 grill 结晶；评审闸在 to-prd 之后）

## 决定

- **「召对夜」是一等实体容器**：夜内是一条连续对话流 + 一本按时间序的**故事账本**。「场」不是硬容器，是「宣 X」事件天然切出的**软段**（供呈现分幕、入档起名）；硬状态极少（夜开着/收了、到没到结算边界一类）。
- **账本条目日记式开放**：硬骨架只留机器必读的两样——先后顺序、涉及人名单（人数不设上限）；正文自由书写；条目类型是**开放标签不是死枚举**。判据=「能读明白」。任一时刻「谁在场/谁殿侧侍立」由进出账推出，供 #459 见闻派生（参与即知）。
- **账的来源与方向：落账不许可**。玩家口令（宣 X）确定性落账；LLM 叙事**演完后抽取落账**（同邸报→delta 模式）。基座对故事基本信任，只做廉价死账校验（如已死者不能在场），不做事前审批——LLM 编出的戏（乾清宫一夜毕自严替洪承畴站台）必须有地方落账，供 #459 见闻、方向 10 关系账、restore 消费；账本再喂回后续故事（毕自严上月作过保，LLM 下次编戏知道）。

## 为什么

连场编排的全部难点（殿侧侍立、插话、当面站台、先发明旨对后入殿者扩散）在「夜→场硬容器」模型里都是绕边界的特例，在事件账本里全是自然情形；P1 restore = 账本即存档，天然精确到最后一笔账。北极星「乾清宫一夜」原文本来就是连续的一夜，站台是 LLM 未经预设编出的好戏——基座的职责是接住它，不是事先批准它（用户 2026-07-02 拍：基座为故事服务；账本开放如日记，能读明白就行）。

## 否决的备选（防日后重议）

- **夜→场两级硬容器（每场固定名单）**：毕自严殿侧插话「算哪场」是伪问题，硬边界逼设计回答一堆这类特例。
- **场为唯一实体 + 指针连场**：「一夜」没有自己的家，跨场规则条条顺链重建，把北极星核心体验（连场）做成二等公民。
- **死枚举事件类型 + 固定字段 schema**：LLM 编出新戏就要改结构，违背「特征化不约束」（ADR 0033）的精神——约束把戏压扁。
