## #1900 修订（2026-09-30，owner 裁定）

源卷 `~/.claude/projects/-Users-akagilnc-WorkSpace-Ming-LLM/a45c2e6b-8c9a-4f56-85fb-73324ee40299.jsonl`：assistant `c8d29698-4c00-4c39-a83c-71084d18ebea` 提议「押解默认算在拨银旨里，密令只管暗中护送」并说明暗护挂当夜已记录的拨银；owner `f6c00308-93f0-40ba-b9ec-33b6cc1d0c19` 逐字答「对的。不要乱加关联」。据此**修订本 ADR 两处前提**，其余（单向新指旧、禁双向互写、效果回指、关联链不带状态位）全部保留不动：

1. **普通押解不另立密令**。平常「拨银三十万去宁远，着某某押解护送」，押解人写进**同一道拨银交办**的 `grant.escort.escortees`，条目照 ADR 0053 参与人形状（人物 id／机械档／职分／委派人），落进本案卷 `participant_roster` 单一真源——代码只 normalize 与校验，不猜机械档。不另建密令案卷、不另挂本案卷关联槽。本槽此后**只管另行暗中加派的护送**（密令案卷单向新指旧 → 已记录的拨银交办）。原先「关联槽是护送关系的唯一载体」的前提就此作废。
   **同夜暂存交办也可承接**：暗护密令与拨银同夜一道下达时，拨银此刻只有暂存（`pending_actions`）没有案卷。密令声明按本夜暂存清单里的 action id 指过去（`escort_pending_targets`），密令成案时把指向持久化在密令案卷载荷，等该拨银收夜成案再承接。
   **承接方向为何记在拨银案卷一侧**：真实入口里**密令先成案**——「密令应允即落地」是 ADR 0038 夜内直写白名单①，拨银拟旨只标已应允、收夜才成案，所以暗护密令案卷的 id 必然更小。本 ADR 的关联槽要求新案卷指向旧案卷，装不下这个方向；票面又同时禁「提前拨银成案」与「双向互写」。因此这一条单向回指记在**后成案的拨银案卷**载荷 `escort_sources` 上：新案卷指旧案卷，单向、不双向互写、不提前成案、通用新指旧校验一字未松（`add_dossier_links` 对本路径完全不参与）。已记录的旧拨银仍走关联槽。`record_dossier_escort_result` 的护行主体凭据按这两条真源合取（`_escort_source_relation`），关系类型一律取自既有记录，不接受声明另报。
2. **对账不凭关联判有护**。关联只答「谁护谁」，不是「这趟护成了」。逐路实际护送落 `dossier_escort_outcomes`（被护案卷×回合一行，唯一真源），月度拨帑核算只读它：一令护多路有成有败各读各路，成功护送后密令结案仍按该路已落的有护对账，未实际护送的路不得只凭关联当作有护。

**旧软判实抵相抵段作废**：#1820 后实抵与沿途损耗归引擎（`grant_arrival_bounds` 按有护/无护既有折损范围取值），原「LLM 提实抵提案 + 代码 clamp」的口（`dossier_reconciliations` 提案节、`clamp_grant_arrival_amount` 及其坏提案拒收族）已退役。护行界严于无护行，两者仍由引擎定，不新增目的地现金账户、不二次扣库。
