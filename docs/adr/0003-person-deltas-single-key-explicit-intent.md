# 人物相关 delta 用单 key + 显式动作意图

Status: accepted（实现 deferred，见末节）

涉及人物的结算 delta 现在分散在四个顶层 key：`office_changes`(任免)、`character_status_changes`(存殁去向)、`character_power_changes`(易主)、`appointments`(后宫册封)。它们在存储层都写 `characters` 表，但每个声明一种**意图**，引擎据此跑不同级联（任免→绑官位 + 踢掉占同坑的旧任者 + 复活 active；存殁→清空 office + 削职 + 应连动派系 leverage；易主→翻 power_id；册封→后宫专用）。

我们决定：**长期把这四个合并成一个顶层 key `人物变更`，每项显式带 `动作` 意图字段，由单一管线按 `动作` 分发**；而不是继续维持四个易混的 key，也不是退化成一个"字段袋"靠出现了哪些字段反推意图。

## Considered Options

- **维持多 key（现状）**：管线已存在、已测试，但四个中文 key 语义边界靠人记，`人事变更`/`人物状态变化` 字面像到手滑。实证翻车：turn21 把"毛文龙 dead"产进 `人事变更`(office_changes)，因缺 `new_office` 被静默拒收，毛在 DB 里没死（见 issue #13/#12）。
- **改名缓解（`职务任免`/`人物状态变更`）**：零重叠 token 能降低手滑率，但**不消除**"填错 key"这个失败类；且合并后名字还要再变，是会被推翻的临时工。**已否决**。
- **合并成字段袋 `character_delta{任意字段}`**：一个 key，但引擎必须从"出现了哪些字段"反推意图——正是斩毛 bug 的死因，反推意图更中心化，**更**脆。**已否决**。
- **合并成单 key + 显式 `动作`**：一个 key 杜绝填错 key；意图是声明的、不靠反推；`动作` 未知值可响亮拒收。两类失败一起消灭。**采纳**。

## Consequences

- 产 delta 时人物变动只进 `人物变更`，每项必带 `动作`∈{任免, 存殁, 易主, 册封}（最终枚举待实现时定）+ 该意图的 payload。
- 单管线按 `动作` 分发到现有四套级联逻辑；未知 `动作` 或 payload 缺字段 → **响亮拒收（不静默吞）**，与 issue #14"静默吞异常"治理同向。
- 旧四 key 作为 alias 兼容层可保留一段（避免一次性破坏历史产出端），但 prompt 契约(`score_extractor_*.md`)迁到新 key。
- DELTA_SCHEMA.md 的人物相关条目需同步重写。

## 实现时机（deferred）

本决策**现在不实现**。它涉及合并四条 apply 管线 + 重写 prompt 契约 + 改 DELTA_SCHEMA，改动面与 issue #3(事务边界)、#14(静默吞收集器)、以及 codex 进行中的 channel 分支相邻，宜在重构波统一做，不在当前小批(#4/#10)里抢工期。issue #13 已据此重定性为该合并的载体。
