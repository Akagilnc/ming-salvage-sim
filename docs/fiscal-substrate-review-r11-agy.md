### 1. §0.1 新守恒断言及三条对账公式评审

#### ① 新主断言（现金双边平）的正确性与漏洞
当前的现金主断言在默认测试数据下能跑平，但**在数学设计上存在两个致命漏洞**。一旦引入外部资金拨付或清欠动作，该断言会**直接失效（FAIL）**：

*   **漏洞 A：漏掉外部拨付项（`拨付net`）**
    `拨付net`（协饷/省际调拨）是外部流入本省的现金。它不属于本地的`民间流出`，但会直接进入`省内可支`并增加`省库库银`（或被消费）。
    *   **数学不匹配**：若 $拨付net > 0$，则 $\Delta(\Sigma CASH)$ 增加，但等式右侧的 $民间流出 - 受款方流入$ 保持不变，导致两边不平。
    *   **修正**：必须在主断言中加入该项：
        $$\Delta(\Sigma CASH) == 民间流出 - 受款方流入 + 拨付net$$
*   **漏洞 B：漏掉民间清欠（`清欠`）**
    当执行清欠 Action 时，民间将积欠的旧赋折现交出。这笔钱属于边界外的`民间`流入系统 CASH，会增加`省库库银`。
    *   **数学不匹配**：若主断言的 `民间流出` 仅定义为 `实征 + 火耗实收`，则清欠入库的资金会导致等式左边偏大，右边偏小。
    *   **修正**：`民间流出` 的口径必须包含清欠：
        $$民间流出 = 实征 + 火耗实收 + 清欠$$

#### ② 三条对账公式的自洽性
*   **债务对账（B）的自洽性与截断风险（Issue）**：
    公式为：`B.负债_new = B.负债_old + NewDebt_i − Repaid_i`。
    *   **风险点**：在 Spike 的 Action 阶段（步骤 ⓪），若补饷 Action 的 `eff_cost` 超过了未清偿债务 `claim['军饷欠']`，Spike 会使用 `max(0, ...)` 将债务归零。此时，**实际冲销的债务**是 `B.负债_old`，而**付出的现金**是 `eff_cost`。
    *   **自洽性破损**：若在债务对账中 `Repaid_i` 采用 `eff_cost`，等式将不平（会出现负数债权）。因此必须明确规约：
        $$Repaid\_i = \min(eff\_cost, B.负债\_old)$$
*   **C 灰账对账的自洽性**：
    公式为：`C_new = C_old + 火耗实收 + 漂没 + 中饱 + eff损耗 − (追赃+挪借)`。
    *   **结论**：该公式逻辑自洽。它正确地将所有流入非 official 库银的损耗/截留定义为 C 的流入，将挪借/追赃回省库的动作定义为流出（属于 CASH 内部的子账户转移，不影响 $\Delta(\Sigma CASH)$ 总额）。
    *   **但需注意**：必须在规范中严格限制 `挪借` 与 `追赃` 的流向——它们只能去往 `省库库银`。若流向系统外，则会打破此消彼长的守恒。

#### ③ 旧 tautology（82=...）废得对吗？
*   **结论**：**废除得完全正确**。
*   **原因**：旧公式 `应征 ≡ 实征 + 民欠` 属于纯代数定义。无论计算省库结转的代码写得多么混乱（哪怕资金凭空蒸发或双扣），因为 `应征` 侧的等式属于静态公式展开，它永远能通过校验。只有基于**系统边界流出/流入（Double-Entry）**的真复式断言，才能作为防 Bug 屏障。

### 2. Spike 代码与 v11 Spec 一致性及「假 PASS」漏洞分析

#### ① Spec ↔ Code 不一致与“假 PASS”
*   **`拨付net` 假 PASS 漏洞**：
    在 Spike 代码中，`拨付net = params.get('拨付net', 0.0)` 已经参与了 `省内可支` 的运算，并影响了期末的 `省库库银`。但是在最后的守恒校验中：
    `净流 = 民间流出 - 受款方流入`
    `ok_cash = abs(Δcash - 净流) < 1e-6`
    **完全没有引入 `拨付net`**。目前 G1/G2 能够 PASS，仅仅是因为测试用例中的 `拨付net` 被设为了 `0`。一旦将 `拨付net` 设为大于 0 的数值，该 Spike 必然 FAIL。这属于典型的“假 PASS”测试设计。
*   **丢失的 Flow 汇总**：
    v11 Spec 规定“清欠/追赃/挪借入库 target 走 Flow 入库”，且应在步骤 ⑪ 计入 `省内可支`。但 Spike 中的 `省内可支` 仅硬编码了 `省库库银_post + 省内池 + 拨付net`，缺失了清欠、追赃等动作产生的临时 Flow 现金流入通路。

#### ② 业务逻辑漏洞（防双扣失效）
*   **防双扣纯依赖人工**：
    Spec 限制“支付类 Action（补饷/赈济）银 Cost 即该笔支付，不再另记 Due”。但是在 Spike 中没有对此做任何代码级的校验或保护。若场景配置者同时在 `actions` 和 `Due` 中配置了同一笔款项，Spike 会扣款两次（一次在 ⓪ 阶段扣除 `eff_cost`，一次在 ⑪ 阶段扣除 `Paid`），且因为两笔钱都进入了 `to_受款方`，**守恒断言依然会平（PASS），但实际上发生了严重的业务逻辑双扣 Bug**。

### 3. 骨架约束力评估：Spine 现在锁得住吗？

**结论：完全锁不住。** 

仅凭 v11 Spec 和当前的 Spike，两个没有沟通的开发者写出的模拟引擎会在以下核心机制上产生巨大偏离：

1.  **Modifier 机制完全缺失**：
    Spec 声明了 `V_final = clamp(V_base * ∏max(0, 1+scale) + Σdelta)` 以及 `modifier衰减`，但 Spike 里一行修饰符的处理代码都没有。修饰符在每月的哪个阶段衰减？叠加时的优先级（如先乘后加还是先加后乘）如何？钱类 Stock 禁 scale 的底层阻断逻辑怎么写？这都是未解之谜。
2.  **具体 Action 的数学公式未标准化**：
    如 G3「清丈」。清丈导致“隐田↓官民田↑”，这到底是一个 `delta` 还是一个百分比 `scale`？士绅阻力（阻碍税收/降低k）的数学反馈回路是什么？没有 Spike 给出 Golden 算法，两个开发者会各自发明一套曲线。
3.  **损失与摩擦力的扣除规则未细化**：
    当发生“中饱”或“eff损耗”时，它们是从支付给受款方的金额中扣除（扣除后才叫 `实付`），还是在支付金额之外额外扣除？Spike 没有实现这部分逻辑，规范里也没有详细定义 Flow 扣减关系。

### 4. 未覆盖路径守恒风险分析（清丈/挪借火耗/漂没/效率损耗）

这些未在 Spike 中编写测试代码的路径，藏着能轻易击穿守恒的“隐形地雷”：

#### ① 清欠路径（破守恒风险：极高）
*   **风险**：清欠动作会将 `民欠旧赋` (CLAIM) 转化为 `省库库银` (CASH)。如果不将清欠款项追加到主断言的 `民间流出` 因子中（即保持旧公式），**现金主断言必破**，因为系统内多出了现金，而边界流出没有记录。

#### ② 挪借火耗路径（破守恒风险：中）
*   **风险**：挪借火耗（C 灰账 $\to$ 省库库银）属于 CASH 内部划拨。
    *   如果实现者没有同步将 `C_地方截留` 扣减，而是直接通过 Flow 增加 `省内可支`，等同于凭空印钱，主断言和 C 灰账都会失衡。
    *   必须在底层的 `transfer_to` 接口中，强制将此类动作声明为**双向账户冲销**（Source 账户必须真实减少，Target 账户同步增加，且该过程受 k 值缩减约束）。

#### ③ 效率损耗（eff损耗）与中饱路径（破守恒风险：高）
*   **风险**：如果实付军饷为 45，由于效率损耗 10%（即 4.5 两）：
    *   若省库支出了 45 两，中饱了 4.5 两（进入 `C_中饱`），士兵只拿到 40.5 两（进入 `受款方`）。
    *   那么 $\Delta CASH$ 仅减少了 40.5 两（省内库银 $-45$，但 C 灰账 $+4.5$）。
    *   此时，如果 `受款方流入` 错误地记录了**名义实付金额**（45 两），则主断言会出现：
        $$-40.5 \text{ (ΔCASH)} \neq -45 \text{ (民间流出 - 受款方流入)}$$
        导致守恒断言直接 FAIL。
    *   **规约要求**：必须在 Spec 中明确规定，**`受款方流入` 在记账时必须扣除所有中间损耗/中饱（即记净值流入）**，或者主断言等式右侧必须减去损耗项。
