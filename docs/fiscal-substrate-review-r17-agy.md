# r17 · agy(holistic v17)

在对**省级财政基座 v17**设计规范与附带的**Spike验证脚本**进行深度的逻辑推演和公式校对后，本次整体评审发现几处隐蔽的代码实现 Bug 与对账设计漏洞。

若将这几处问题修复，整体设计即处于极佳的自洽状态，**“可收敛并开始 port”**。以下为具体文字评审：

---

### 一、 v17 设计规范 (Spec) 评审

1. **历史与玩法对齐：**
   * **三饷时间线与增量注入**：规范中明确“三饷分时间线注入”非常关键。辽饷（天启/崇祯初已存在且在崇祯四年加派）、剿饷（崇祯十年十年的“十面张网”）、练饷（崇祯十一年）。在具体 Port 进引擎时，三饷数值在 `p` 中不应为固定常量，需根据游戏 Tick 对应的历史月份动态解算输入，玩法设计符合史实。
   * **退出通道与软判设计**：死亡螺旋的上行破局交给 AI 软判（如招抚流民、挪借、截留起运带来的弹劾代价），账本引擎仅负责刚性的“记账与守恒”。这种“铁律引擎 + 柔软裁判”的分工非常巧妙，避免了数值死局，保障了玩法宽度。

2. **支付类与行政成本类 Action 的区分**：
   * 规范中“支付类（补饷/赈济）”其 `cost` 即为支付本身，行政成本类则只扣成本并触发 effect。这一规约有效规避了“双重扣款”漏洞，并在 Spike 中得到了成功实证。

---

### 二、 Spike 代码逻辑缺陷与安全漏洞评审

虽然 Spike 在运行 G1–G14 时均显示 `PASS`，但这是因为测试用例（G1–G14）中所有的转移/征收类 Action（如 `挪借火耗`、`追赃`、`清欠`、`蠲免`）均将 `cost` 默认设置为 `0`。一旦有带行政成本的同类 Action 传入，将会触发以下**严重 Bug**：

#### 1. 征收/转移类 Action 的行政成本未真扣 (逻辑 Bug)
* **缺陷表现**：在 [spike_settle_tick.py](file:///tmp/ming_agy_sandbox/spike_settle_tick.py) 的 `⓪ action phase` 执行循环中：
  对于 `清丈` 和 `营建`，代码正确地执行了：
  ```python
  if ec > 0: cash['省库库银'] -= ec; cash_out += ec; r['行政补饷'] += ec
  ```
  但对于 `挪借火耗`、`追赃`、`清欠`、`蠲免`，代码**完全遗漏**了对 `ec`（行政成本）的扣减。
* **后果**：如果执行 `dict(type='清欠', amount=10, cost=5)`，该 5 两成本会进入 `ΣCost` 参与算 `k`（导致其他 Action 的力度被等比例缩减），但**省库库银却从未扣除这 5 两现金**。这违反了 Spec §9 “征收/转移类 action 若带 cost，该成本必须真从省库扣”的铁律。
* **修复方案**：在 Action 执行分支中，对这些转移类 Action 补充行政成本扣减：
  ```python
  if t in ('挪借火耗', '追赃', '清欠', '蠲免'):
      if ec > 0: cash['省库库银'] -= ec; cash_out += ec; r['行政补饷'] += ec
  ```

#### 2. 债务 Oracle 的“同源中间量泄露” (对账安全性漏洞)
* **缺陷表现**：Spike 在重算债务 Oracle 的期望值时，读取了结算过程中的**运行时中间变量**：
  ```python
  o_pool = 省内可支
  ```
* **后果**：这破坏了 r13-r15 确立的“绝对独立对账（No Tautology）”原则。如果由于前述的“成本未扣除 Bug”导致 runtime 中的 `省内可支` 偏大，Oracle 会直接采用这个偏大的错误值去分配付款与还债，导致**债务对账无法捕获这个 Bug**。
* **修复方案**：在 Port 时（或在 Spike 中），`o_pool` 的期望值必须完全从开账快照 `st` + 参数 `p` + `actions` 独立重算：
  ```python
  # 完全独立重构省库后态，不读 settlement 局部变量
  o_Stock_post = o_Stock  # 初始库银
  for a in actions:
      ak = o_k if a.get('cost',0) > 0 else 1.0
      ec = a.get('cost',0) * o_k
      t = a['type']
      if t == '补饷':
          o_Stock_post -= min(ec, claim0['军饷欠'])
      else:
          if ec > 0: o_Stock_post -= ec
          if t == '挪借火耗':
              o_Stock_post += min(a.get('amount',0)*ak, st.get('C_地方截留',0)) * a.get('eff',1.0)
          elif t == '追赃':
              o_Stock_post += min(a.get('amount',0)*ak, st.get('C_中饱',0)) * a.get('eff',1.0)
          elif t == '清欠':
              o_Stock_post += min(a.get('amount',0)*ak, claim0['民欠旧赋'])
              
  o_Stock_post += g * (1 - zb)  # 加上拨付 net
  o_pool = o_Stock_post + max(0.0, 实征_o - 起运池_o)  # 得到真正的独立可支池
  ```

#### 3. 缺少 `unmet_relief` 输出 (指标遗漏)
* **缺陷表现**：Spec §9 要求引擎必须向外输出 `unmet_relief` (= `Due_4 - 实付`) 供 LLM 裁判评估社会矛盾。目前的 Spike 中虽计算了赈济的实付，但在最后的 `new_st` 返回字典中没有携带该统计字段。
* **修复方案**：在返回字典中补充：
  ```python
  new_st['unmet_relief'] = p['Due'].get('赈济',0) - r['实付'] (若只针对赈济付款的话)
  ```

### 三、 评审结论

**挑出了细节缺陷，但“骨架已极度扎实，可以收敛/Port”。**

以上发现的 3 个问题均属于“实现层面的漏网之鱼”，而非设计哲学（ADR 0007）或物理守恒公式的缺陷。
* 在把验证通过的逻辑正式 port 到 `ming_sim`（真引擎）中时，**必须将上述 1、2、3 项修复代码合入**。
* 修复后，Spike 沉淀的 **G1–G14 用例完全可以作为 pytest 的黄金锚点测试集**，用于锁死后续跨省 Hub 等扩展开发时的重构安全性。
