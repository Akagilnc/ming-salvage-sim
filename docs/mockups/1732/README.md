### 票面文案清单（9 + 1）

1. `将撤回最近一轮召对及其政务影响，是否继续？`
2. 拟诏无参 → mock 补文：`本月无可颁诏草案，仍有失败密令未处理。确认不经盖玺颁诏、直接退朝结束本月？`

4. `确定重开新局？当前局所有数据将被永久清空（存档目录不动）。`
5. `回到主菜单？当前对局会关闭（DB 仍保留，可从「继续上局」回到此处）。`
6. `退出整个游戏？前后端进程都会关闭，未保存的进度会丢失。`
7. `删除 N.db？`
8. `将覆盖当前主进度，是否继续？建议先在游戏中保存为存档。`

## A · 统一奏疏牌

**取向**  
所有 `confirm` / `alert` 换成同一组件：画面中央「奏疏牌」——左边朱条、事由标题、正文（票面原句）、可选后果条、准/驳。高危只在牌内加码（重开的手打解锁），不另起交互族。

**各代表场景**

- 回到主菜单：说明面板保留作导引；点按钮 → 奏疏牌一次授权（无原生框）。
- 重开新局：面板按钮只唤起牌；牌内手打「重开」后解锁确定。
- 拟诏：主钮 → 同形奏疏牌，正文为补全的退朝说明。

**代价**

- 低危与高危共用骨架，若不分视觉权重，容易「看起来都一样重」。
- 已有完整说明面板的动作仍会再出一次牌——双重确认从「原生」变成「画面内」，次数未必减到 1（除非实现时对这批白名单直通）。
- 全仓一刀切，改动面集中，但任何文案/分级微调都碰同一组件。

**不包含的结论**  
不预设「必须保留第二次确认」或「必须直通」；只展示统一承载形态。

## B · 就地消解

**取向**  
先问：这个动作**是不是已经有**一整块「标题 + 后果 + 按钮」？  
有 → 面板即确认，票面 `confirm` 原句并入面板作可见后果句，按钮**直接执行**（结构性拆掉双重确认）。  
无 → 在动作原位长出贴身条（行内 / composer 上 / 页脚 / 主菜单深色卡），仍不进系统框。

**各代表场景**

- 回到主菜单：面板已含说明 + 并入的 confirm 原句 → 一点即行，零第二次。
- 重开新局：手打「重开」留在面板原位，解锁后直接 `reset`，无第二次。
- 拟诏：无既有说明面 → 页脚展开确认条，补退朝文案。

**代价**

- 交互形态分裂：面板直通、行内展开、页脚条、深色菜单卡、告警条……实现与 QA 要记多套。
- 「看起来不像同一种确认」，品牌一致性弱于 A/C。
- 直通后误触成本上升（尤其退出游戏、加载覆盖）——只能靠面板文案与按钮视觉，没有第二道闸。
- 列表行展开可能挤布局，长文案在窄行不好读。

**不包含的结论**  
不预设直通一定优于二次确认；只展示「以原位为第一公民」的极限形态。

## C · 风险分阶

**取向**  
用**三种书案形态**编码不可逆程度，让玩家未读字先读阶：

| 阶 | 形态 | 本 mock 归入 |
| --- | --- | --- |
| 一阶 | 底栏纸签（轻、不挡全屏） | 撤回召对、拟诏 failed-only 退朝、上传失败 alert |
| 二阶 | 中央奏疏牌 | 回主菜单、加载、退出、删档、覆盖主进度 |
| 三阶 | 御案朱批卷轴 + 手打解锁 | 仅重开新局 |

**各代表场景**

- 回到主菜单：导引面板 + **一次**二阶奏疏（原生框去掉；不升到三阶）。
- 重开新局：三阶朱批案，手打「重开」绑在案上。
- 拟诏：一阶轻签 + 补文；不抬成奏疏牌，避免与盖玺颁诏的视觉重量打架。

**代价**

- 三套 UI + 一张分级表要维护；调用点加确认都要先议阶。
- 分阶主观：例如「删除存档」放二阶还是三阶、`退出游戏` 是否应升阶，会争论。
- 错分阶有产品后果：清库若被做成一阶会弱授权；低危做成三阶会过扰。
- 实现复杂度高于 A，一致性叙事强于 B。

**不包含的结论**  
表中分级是可讨论草案，不是拍定。owner 可整阶平移单条调用点。

| 自动化点通 | 画面内可点 | 画面内可点 | 画面内可点 |

## 验收对照（实现阶段，非本 mock 范围）

本目录只服务呈现拍板。实现票仍以冻结票面为准，包括但不限于：

- `web/src` 生产代码 `window.confirm` / `alert` / `prompt` 零命中
- 每处可读到要做什么、后果、可否撤销
- 空白确认补文或按真实语义处置
- 已有页面内确认面板的动作不再第二次确认（若拍 B 或 C 的「一次授权」）
- 重开手打解锁不削弱
- 可被自动化浏览器真实点通
- vitest 全绿
