## A · 统一奏疏牌

**取向**  
所有 `confirm` / `alert` 换成同一组件：画面中央「奏疏牌」——左边朱条、事由标题、正文（票面原句）、可选后果条、准/驳。高危只在牌内加码（重开的手打解锁），不另起交互族。

**代价**

- 低危与高危共用骨架，若不分视觉权重，容易「看起来都一样重」。
- 已有完整说明面板的动作仍会再出一次牌——双重确认从「原生」变成「画面内」，次数未必减到 1。
- 全仓一刀切，改动面集中，但任何文案/分级微调都碰同一组件。

---

## B · 就地消解

**取向**  
先问：这个动作**是不是已经有**一整块「标题 + 后果 + 按钮」？  
有 → 面板即确认，票面 `confirm` 原句并入面板作可见后果句，按钮**直接执行**。  
无 → 在动作原位长出贴身条（行内 / 页脚 / 主菜单深色卡 / 底栏告警），仍不进系统框。

**代价**

- 交互形态分裂：面板直通、行内展开、页脚条、深色菜单卡、告警条……实现与 QA 要记多套。
- 「看起来不像同一种确认」，品牌一致性弱于 A/C。
- 直通后误触成本上升（尤其退出游戏、加载覆盖）——只能靠面板文案与按钮视觉，没有第二道闸。
- 列表行展开可能挤布局，长文案在窄行不好读。

## C · 风险分阶

**取向**  
用**三种书案形态**编码不可逆程度，让玩家未读字先读阶：

| 阶 | 形态 | 本 mock 归入 |
| --- | --- | --- |
| 一阶 | 底栏纸签（轻、不挡全屏） | 撤回召对、拟诏 failed-only 退朝、上传失败 alert |
| 二阶 | 中央奏疏牌 | 回主菜单、加载、退出、删档、覆盖主进度 |
| 三阶 | 御案朱批卷轴 + 手打解锁 | 仅重开新局 |

**代价**

- 三套 UI + 一张分级表要维护；调用点加确认都要先议阶。
- 分阶主观：例如「删除存档」放二阶还是三阶、`退出游戏` 是否应升阶，会争论。
- 错分阶有产品后果：清库若被做成一阶会弱授权；低危做成三阶会过扰。
- 实现复杂度高于 A，一致性叙事强于 B。

## 对照（只陈述差异，不排序）

| 维度 | A 统一奏疏牌 | B 就地消解 | C 风险分阶 |
| --- | --- | --- | --- |
| 双重确认（回主菜单等） | 面板 + 牌，仍可能两次画面内 | 面板一次直通 | 面板 + 一次二阶牌 |
| 重开授权 | 牌内手打 | 面板内手打 | 朱批案内手打 |
| 空白 confirm | 同形牌补文 | 页脚条补文 | 一阶签补文 |
| 视觉与书案 | 单一奏疏语汇 | 多原位、语汇散 | 三阶语汇，形态=风险 |
| 实现/维护 | 一组件 | 多接缝 | 三组件 + 分级表 |
| 误触 | 中（有第二次点） | 高（直通） | 随阶变化 |
| 自动化点通 | 画面内可点 | 画面内可点 | 画面内可点 |

## 验收对照（实现阶段，非本 mock 范围）

本目录只服务呈现拍板。实现票仍以冻结票面为准，包括但不限于：

- `web/src` 生产代码 `window.confirm` / `alert` / `prompt` 零命中
- 每处可读到要做什么、后果、可否撤销
- 空白确认补文或按真实语义处置
- 已有页面内确认面板的动作不再第二次确认（若拍 B 或 C 的「一次授权」）
- 重开手打解锁不削弱
- 可被自动化浏览器真实点通
- vitest 全绿
