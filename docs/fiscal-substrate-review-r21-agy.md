# r21 · agy(v21:已收敛可port)

根据对明末崇祯「省级财政基座」v21 方案及 Python spike 原型的整体评审，结论如下：

**挑不出实质性设计与逻辑缺陷，判定「已收敛」，完全具备 port（移植入引擎）的条件。**

以下为针对 v21 设计与 spike 代码的具体文字评审：

---

### 一、 v21 设计评审

1. **四层断言与对账机制（极佳）**
   * **独立 Oracle 设计**：避开了将落账中间变量直接作为期望值的同源谬误（Tautology）。通过完全从输入重算 `k`、债务 waterfall 和 C 分账，能够精准拦截类似「将中饱资金 relabel 进国库」或「将火耗截留 relabel 进军饷」的一致性作弊/逻辑偏移。
   * **末态硬期望锚点**：第 4 类断言（G1–G20 显式末态硬期望）起到了最后的安全网作用，即使未来移植引擎时有极隐蔽的同源流水污染，也能通过常量硬比对直接暴露。
2. **史实与机制契合度（符合铁律）**
   * **时序不对称性**：挪借/追赃在 ⓪ 执行，取期初存量；本 tick 新增的火耗在 ⑦、中饱在 ⑩ 产生，必须下 tick 才能动用。这极其真实地模拟了明代「当月火耗，当月无法调拨」的官僚迟滞。
   * **清丈与土地守恒**：`官民田` 与 `隐田` 的总量守恒锁死，防止了清丈凭空造地（违反铁律中「禁止爽感/科技树」的设定），清丈纯粹是税基的重分类。
   * **赈济不积欠与 `unmet_relief`**：赈济未能支付的部分不转为国家负债（灾民无法向官府索要欠款），但输出 `unmet_relief` 给 LLM 裁判作为民怨和动乱的输入，逻辑链完整。

### 二、 Spike 源码评审

1. **现金流守恒（完全闭合）**
   * 经过对 `xfer_internal` 内部转移、起运分池、漂没/中饱分账的细致推导，`CASH` 与 `BOUNDARY` 的数学公式在任何分支下均能保证 `Δ(ΣCASH) == CASH_in - CASH_out`，无资金凭空产生或消失。
   * 即使在 `补饷` clamp（欠 5 万两但预算锁了 30 万两，实际只花 5 万两）的非对称损耗情况下，余银不花退回省库，守恒式依然完美收拢。
2. **残留点评估（不影响 Port）**
   * **`o_pool` 依赖**：Spike 中债务 oracle 的 `o_pool` 读取了运行时的 `省内可支`。虽然严格来说并非 100% 独立，但由于其被 C 分账独立 oracle、现金守恒以及末态硬期望三重兜底，此残留不构成实质性漏洞，可在移植期保留或微调。
   * **浮点数精度**：Python spike 使用了 float 和 `EPS = 1e-6`。在最终移植入游戏引擎（Golang/C++/TS等）时，**强烈建议使用定点数（Fixed-point Decimals）或以最小货币单位（文/分）作为整数存储**，防止跨多 tick 后的微小浮点误差累积导致断言失效。
   * **输入校验补充建议**：虽然 actions 的输入校验已极度完善（负值、未知 action 均 fail-loud），但在移植时，建议对参数 `p` 中的 `Due` 各科目及 `正赋亩额` 等也增加防负值校验，以实现引擎级的全面健壮性。

### 总结
本套设计及 spike 在经历 21 轮迭代后已极具弹性与鲁棒性，挑不出实质影响正确性的漏洞，**已收敛，可立即开始向主引擎移植（Port）**。
