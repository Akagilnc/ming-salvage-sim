# r5 · grok-4.3(v5)

**spine 可锁，可开写引擎。**

### 1. spine 锁得住吗？
已锁得住。「两个不沟通的实现者会写出同一个 tick 引擎」这个标准，现在只差**极小的执行细节**，而不是架构或顺序。

v5 把关键的**确定性锚点**都钉死了：
- action phase 明确在 tick 开头 resolve，后续所有步骤都读 resolve 后的状态。
- duration 强制走「只读基线 + modifier 栈」，禁止 imperative 改值+反向操作。
- 多 effect 原子性明确「按比例同比缩」。
- 国库边界、起运不足规则、B 入账用 current_due_gap 临时池、C 可追回 vs sink 都写成不可二义的规则。

只要两个实现者都严格按 §2 的 ①-⑪ 顺序 + §6 执行契约走，出来的 monthly settlement 结果会一致。剩下的只是「具体 f() 怎么写」（逋赋率、负担率等函数形状），这属于实现细节，不影响 spine。

### 2. r4 那些点真闭账了吗？
基本都真闭了，不是只改字面：

- **省库 stock**：已作为一级状态明确存在，结转公式写死在不变式里。
- **国库全局边界**：已把「国库入账」彻底移出省级 tick，省级只剩两个接口，边界清晰。
- **民欠语义**：已彻底删除「官偿还民欠」，只剩清欠/蠲免两条路径，付款表里也明确排除。
- **多 effect 原子性**：已写明「付不起就整体同比缩」，不再允许部分生效。
- **duration modifier 栈**：已明确「只读基线 + 动态叠加」，并禁止 imperative 回滚，解决了之前最危险的交织漂移问题。
- **C 可追回**：已拆成 recoverable（C→A）和 sink 两类，追赃路径也写明。

这些都已经从「描述性」变成了「契约性」约束，引擎必须按此实现。

### 3. 还有没有会逼回来改架构的隐藏问题？
没有。

v5 把之前最容易引发架构回滚的几个雷（action 时序、modifier 污染、原子性、跨期 stock、国库边界、民欠方向）都用**契约**的方式锁死了。只要后续实现严格遵守 §6 执行契约附录，就不会因为「实现起来发现不对」而被迫改 spine。

唯一可能需要补的只是**待精验**里那些函数形状和数值边界，但这些都是参数/公式层面，不会动结构。

**结论**：spine 已锁死，可以开写引擎了。
