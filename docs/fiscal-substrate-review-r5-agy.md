### 1. 现在 spine 锁得住吗？还差哪一步？
要达到「完全一致的实现」，引擎在数学和逻辑执行流上还差以下**四个确定性细节**：

#### ① Action 扣款的「循环依赖」与「前置判定」
*   **痛点**：Action Phase 在步骤 ⓪（月结前）resolve，此时本月的「省内池」和「拨付 net」尚未算出，即**本月「省内可支」在步骤 ⓪ 是未知数**。如果 Action 消耗的「银」从本月「省内可支」中扣除，将产生因果倒置（Action 影响逋赋率 $\rightarrow$ 影响实征 $\rightarrow$ 影响省内可支 $\rightarrow$ 决定 Action 是否能付得起）。
*   **落锁方案**：
    *   明确 Action 的银两成本**仅能扣减「上月结转省库库银 (Stock)」**。
    *   在步骤 ⓪，设可用余额为 $Stock_{start}$。若本 tick 欲执行的 Action 总成本 $\sum Cost > Stock_{start}$，则触发**同比缩放因子** $k = Stock_{start} / \sum Cost$。
    *   所有 Action 的力度和 effect 均乘以 $k$，实际扣除 $k \times Cost$。步骤 ⓪ 结束后的剩余库银为 $Stock_{post\_action} = \max(0, Stock_{start} - \sum Cost)$。
    *   步骤 ⑪ 的公式修正为：`省内可支 = 省内池 + Stock_post_action + 拨付net`。

#### ② Modifier 栈的「叠加与合成算法」
*   **痛点**：多个 Action 在同一时期修改同一参数（如 $逋赋率$），如果叠加算法不一致（例如：先乘后加，还是先加后乘），数值会漂移。
*   **落锁方案**：定义唯一的 Modifier 叠加公式。对任意属性 $V$，设其只读基线为 $V_{base}$，激活的 Modifier 集合中，乘性修改器（scale）为 $M_{mul}$，加性修改器（delta）为 $M_{add}$，则：
    $$V_{final} = \text{Clamp}\left( V_{base} \times \prod_{m \in M_{mul}} (1 + m.amount) + \sum_{a \in M_{add}} a.amount, \text{Min}, \text{Max} \right)$$
    *（注：若存在 set 覆盖型修改器，直接使 $V_{base} = m.amount$ 后再应用乘加算法）。*

#### ③ Modifier 寿命的「衰减时点」
*   **痛点**：对于 $duration\_months = N$ 的 modifier，是在 Tick 开始时衰减，还是在结算完后衰减？
*   **落锁方案**：统一规定在**步骤 ⓪ 结算开始前**，所有存续 Modifier 的剩余 duration 减 1；减至 0 的 Modifier 立即移出栈。新 resolved 的 Action Modifier 在本 tick 计入，初值为 $N$（本月即生效，算作第 1 个 tick）。

#### ④ 支付 waterfall 与 B 债务偿还的「纯代数描述」
*   **痛点**：自然语言的 "先抵本月缺口，余抵本金" 在编写代码时容易产生分歧。
*   **落锁方案**：
    *   设本月各项应付为 $Due_i$（$i \in \{1:驻军, 2:官俸, 3:宗禄\}$），本月可支为 $Pool = 省内可支$。
    *   按优先级 $1 \rightarrow 3$ 扣减：$Paid_i = \min(Pool, Due_i)$，$Pool \leftarrow Pool - Paid_i$。
    *   若本月有缺口，产生新增欠账：$NewDebt_i = Due_i - Paid_i$。
    *   若扣完 1~4 项后仍有盈余 $S = Pool - Due_4 > 0$，则将 $S$ 顺次偿还旧债 $B_i$（优先级：军饷欠 $\rightarrow$ 宗禄欠 $\rightarrow$ 官俸欠）：
        $Repaid_i = \min(S, B_i)$，$B_i \leftarrow B_i - Repaid_i$，$S \leftarrow S - Repaid_i$。
    *   本月结转库银 $Stock_{end} = S$。
    *   $B_i$ 最终落账：$B_{i, new} = B_{i, old} + NewDebt_i - Repaid_i$。此公式完全消除了“先入账再冲销”的逻辑歧义。

### 2. r4 修正点闭账情况审计
*   **省库库银 stock**：**已真闭账**。通过步骤 ⑪ 的 `上月省库库银` 引入跨期结转，成功打破了原先「月度流清零」的黑箱，平准逻辑在公式上完全成立（只需补齐上述 Action 扣款规则）。
*   **国库全局边界**：**已真闭账**。省级引擎只负责上报 `起运到京` 和接收 `拨付net` 两个接口流，国库由全局 coordinator（LLM/全局步骤 ⑫）统一平账，省级 tick 的自洽性不再受全局国库赤字的干扰。
*   **民欠语义**：**已真闭账**。删除了不合逻辑的「官偿还民欠」，民欠归位为资产负债表中的「应收账款」（B.民欠旧赋）。「清欠」和「蠲免」的流向清晰。
*   **多 effect 原子性**：**已真闭账**。在 §4 和 §6.3 中明确了整包按比例缩减（不白嫖）机制。
*   **C 可追回（灰账）**：**半闭账（存在字面漏洞）**。
    *   *漏洞*：没有交代 `C→A`（清账追赃）后，追回的银两落入哪个流。
    *   *修正*：定义 Action `清账追赃`：扣减 $C_{地方截留}$ 或 $C_{中饱赃银}$ 共 $X$ 万两，折算损失后将 $X \times (1 - 损耗率)$ **直接加计到本月步骤 ⑪ 的「省内可支」中**（作为非正税的一次性额外流入）。
*   **起运不足规则**：**已真闭账**。`起运池 = min(实征, 起运定额)` 逻辑极其冷酷且符合晚明实际：地方实征不足时优先起运解京，省内池直接归零，地方官兵无饷，逼出地方死亡螺旋。

### 3. 会逼回来改架构的隐藏问题？
目前仅剩一个可能影响系统演化的**软轴（State/Spiral）耦合**隐患：
*   **「火耗」的非债务化流失**：
    *   步骤 ⑦ 中，火耗未实收部分（$\text{火耗应派} \times 逋赋率$）直接消失了，没有计入 `B.民欠旧赋`。
    *   *评估*：这在历史上是合理的，因为火耗是附加税（灰/白之间），百姓不交，官府原则上无法作为正税欠赋去追剿（只能私下加征）。但这意味着**火耗没有积欠概念**。如果未来想做“追缴火耗”，架构上会受限。
    *   *结论*：若确认火耗不需要积欠追讨设计，则无需修改架构，直道行之即可。
