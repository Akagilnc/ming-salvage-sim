# r6 · agy/gemini(v6)

### 评审结论：Spine 可锁，但在开写引擎前，必须先补齐 3 个算法细节与 1 个规避“凭空印钱”的架构设计。

以下针对您提出的三个核心问题进行深度评审：

---

### 一、 现在能锁吗？还差哪一步？

从“两个不沟通的实现者写出同一个 tick 引擎”的标准来看，**目前已达到 90%，但还差以下三步明确定义**：

#### 1. 明确定义哪些是 Stock（跨期持久化）和 Flow（每期重置为 0）
引擎必须有一张明确的变量类型清单。如果实现者 A 把某个中间变量当成 Stock 累加，而实现者 B 在 Tick 开始时将其清零，引擎会直接算崩。
*   **Stock 账本**：`省库库银`（来自上期结转）、`B.军饷/官俸/宗禄欠`、`B.民欠旧赋`、`C.地方截留`、`C.中饱赃银`、`民口`、`官民田`。
*   **Flow 账本（每 Tick 开始前重置为 0）**：`本月应征`（正赋/三饷/火耗）、`实征`、`火耗实收`、`起运池`、`省内池`、`起运到京`、`拨付net`、`清欠入库`、`追赃入库`、`省内可支`、`本月应付`、`本月实付`、`新设欠账`、`旧债偿还`。

#### 2. 规定派生变量的“级联计算与修饰器应用顺序”
当一个派生变量依赖于另一个派生变量，且两者都有 modifiers 时，必须规定计算顺序：
*   **级联规则**：必须严格按照月度结算顺序 ①–⑪ 计算。当计算出某变量的初始值时，该值作为 `V_base` 立即应用该变量的修饰器得到 `V_final`。后续步骤中凡是引用该变量，**必须且只能**使用 `V_final`。
*   *示例*：计算起运池时，`起运池 = min(实征_final, 起运定额_final)`，不能使用未应用 modifier 的 base 值。

#### 3. 定义 k 缩减因子对 discrete/enum 类型的效果行为
如果一个 action 的效果（effect）是 `op: set` 且为非数值/离散状态（例如：`政策态 = ACTIVE` 或 `官僚态度 = COOPERATIVE`）：
*   当资金不足导致 $k < 1$ 时，离散状态无法乘以 $k$。
*   **引擎规约**：必须规定 `op: set` 的离散效果是按概率 $k$ 触发，还是在 $k < 1.0$ 时直接失效，亦或是只有 $Cost > 0$ 的 delta 效果缩减。

### 二、 r5 那些公式真闭账了吗？

经过代数推演，核心公式逻辑在闭合性上表现优异，但有 2 处逻辑漏洞和 1 处史实核对需要订正：

#### 1. Action 成本扣减与 $k$ 缩减：**存在 0 成本 action 被无辜波及的 Bug**
*   *现状*：`若 ΣCost > Stock_start，则同比缩 k，所有 action 缩 k`。
*   *漏洞*：如果玩家同时提交了“军事动员（高成本）”和“发布安民告示（0成本政治action）”，由于军事动员太贵导致 $k = 0.1$，如果一刀切，会导致 0 成本的安民告示效果也被缩减到 10%。
*   *修正公式*：
    $$k_{action\_i} = \begin{cases} 1 & \text{若 } Cost_i = 0 \\ \frac{Stock\_start}{\sum_{Cost_j > 0} Cost_j} & \text{若 } Cost_i > 0 \text{ 且 } \sum Cost_j > Stock\_start \end{cases}$$
    仅对有银钱消耗的 action 进行 $k$ 缩减，不波及 0 成本 action。

#### 2. Modifier 唯一叠加公式：**防止乘积项变为负数**
*   *现状*：`V_final = clamp( V_base × ∏(1+scale_i) + Σ(delta_j), min, max )`
*   *隐患*：若存在 `scale_i = -1.2`（即削减 120%），则 $(1 + scale_i) = -0.2$。若有多项负 scale，奇偶相乘可能导致最终乘积项反弹为正，或者出现负值。
*   *修正*：引擎在累乘时，必须对每个乘积因子进行非负 clamp：`∏ max(0, 1 + scale_i)`。此外，永久性 modifiers 建议使用 `duration = -1` 表达，不参与 `duration - 1` 的衰减逻辑。

#### 3. C→A 追赃/清欠落账：**理清 B 账本的借贷属性**
*   *账目澄清*：`B.军饷/官俸/宗禄欠` 是政府的**负债（Payable）**，而 `B.民欠旧赋` 是政府的**债权（Receivable）**。
*   在 §6.5 旧债偿还时，顺次偿还的 $B_i$ 只能包含负债类，千万不能把 `B.民欠旧赋` 算进去，否则变成了“政府拿盈余银子去替百姓还百姓欠政府的税”，逻辑不通。

#### 4. 付款/偿还代数：**确认优先级倒置是设计而非笔误**
*   本月支出优先级：`军饷(1) > 官俸(2) > 宗禄(3)`
*   偿还旧债优先级：`军饷欠 > 宗禄欠 > 官俸欠`（宗室排到了官俸前面）
*   *核对*：若此设计是为了体现明末宗室催逼欠禄的政治压力，则合理；若是笔误，请统一。

### 三、 还有没有会逼回来改架构的隐藏问题？

有 1 个极其致命的“凭空印钱”漏洞，以及 2 个建议保留的架构扩展点：

#### 1. 致命漏洞：Stock 与 Flow 独立 delta 导致“凭空印钱” (Silver Leak)
*   *问题描述*：追赃/清欠在 schema 中被拆成了两个独立的 effects：
    1.  `B.民欠旧赋` delta `-50`
    2.  `清欠入库` delta `50`
*   如果执行时，`B.民欠旧赋` 的 stock 余额实际上只有 `30`。引擎在处理第一个 effect 时，会将其 clamp 在 `0`（即实际只扣了 `30`）。
*   但第二个 effect `清欠入库` 依然会傻傻地增加 `50`。**这就凭空创造了 20 万两银子！**
*   *解决方案*：引入一个显式的 **`transfer_to`** 算子，专门用于 Stock 到 Flow 的转移：
    `{ source: B.民欠旧赋, op: transfer_to, target: 清欠入库, amount: 50, efficiency: 1.0 }`
    引擎执行 `transfer_to` 的逻辑为：
    $$\text{actual} = \min(\text{amount}, \text{source.value})$$
    $$\text{source.value} \gets \text{source.value} - \text{actual}$$
    $$\text{target.value} \gets \text{target.value} + \text{actual} \times \text{efficiency}$$
    这从底层架构上彻底消除了资金不守恒的 Bug。

#### 2. 非银资源（人、权、政治槽）校验边界
*   如果这些资源不足，是否像银钱一样影响 action 的力度 $k$？
*   *架构建议*：在文档中明确声明：“人、权、政治槽等非银资源由 LLM 裁判或外部系统校验，引擎在执行时默认其充足，或仅执行对特定 effect 的 clamp，不进行整组同比缩小。”

#### 3. 必须输出“支出满足率（Paid/Due）”供外部读取
*   军饷欠账会直接引发兵变，赈济不足引发民变。但引擎本身不计算兵变/民变（由LLM裁判）。
*   *架构建议*：引擎在 tick 结束时，必须将本月的 `Paid_i / Due_i`（特别是军饷和赈济）作为只读的 output 字段暴露出来，供裁判系统评估死亡螺旋。

### 评审总结

> [!NOTE]
> **Spine 可锁，可开写引擎。**
> 只要在写引擎代码前，将上述的 **`Stock/Flow 变量清单`**、**`级联计算顺序`**、修正后的 **`0-cost action 不缩水公式`**，以及用于资金转换的 **`transfer_to 算子`** 写入开发规约，即可保证两个不沟通的程序员写出完全一致的 tick 引擎。
