# 明末崇祯财政「省级财政基座」v9 评审意见

本轮评审基于“**两个独立实现者能写出完全一致的 tick 引擎**”这一契约标准，对草表 v9 进行深度逻辑校对。以下为针对三个核心问题的评审意见：

---

## 1. Spine 锁得住吗？——「两个不沟通实现者照此写出同一 tick 引擎」达到没？

**结论**：尚未完全达到。以下 3 处时序和边界逻辑会导致两个实现者写出截然不同的计算结果（分叉点）：

### ① ⓪ 步骤的「因果循环（Causal Loop）」矛盾
*   **分叉描述**：
    *   v9 规定：“`transfer_to` effect 在此立即执行……全部 action resolve 后批量算 $k$，`省库库银_post = Stock_start - Σ(k * 银Cost)`”。
    *   然而，仅 `Cost > 0` 的 action，其 `transfer_to.amount` 需要乘 $k$。
    *   这就产生了死锁：要执行 `transfer`，必须先知道 $k$；而计算 $k$ 却在“所有 action resolve 之后”。
*   **修正契约**：必须明确 ⓪ 的微观时序（Micro-timeline）：
    1.  **收集阶段**：收集本 tick 所有激活 action 申报的 `Cost`（银）。
    2.  **计算调度**：计算全局缩减系数 $k = \min(1, \frac{Stock\_start}{\sum Cost})$。
    3.  **应用阶段**：将 $k$ 作用于所有 action 的 effects（`delta/scale/transfer_to.amount`），然后**执行**这些 effects，并同步更新 `省库库银`（扣除 $k \times Cost$）。

### ② `set` 修正器的生命周期与「基准回滚」分叉
*   **分叉描述**：
    *   v9 提到：`set` 先覆盖 `V_base`；`scale` 在第 4 tick 自动回 base。
    *   如果一个 `set` 修正器的 `duration_months = 3`，当它在第 4 tick 过期时，`V_base` 是否需要恢复到被 `set` 覆盖之前的“历史原始值”？
    *   **实现者 A** 可能认为 `set` 具有永久副作用，直接修改了底层的静态 `V_base`（过期不回滚）。
    *   **实现者 B** 可能在内存中维护了一个 `V_base_original`，当 `set` 修正器过期时，将 `V_base` 回滚到原始值。
*   **修正契约**：明确 `set` 的本质。建议规定：`set` 修正器不应支持有限生命周期（或其 `duration` 恒为 -1/永久），一旦生效即永久改写 `V_base`。若需临时覆盖，应使用 `delta` 或 `scale`。

### ③ 多笔 `transfer_to` 争抢同一源账户的「执行序」分叉
*   **分叉描述**：
    *   若同一 tick 内有两笔 action 同时从 `省库库银` 转出（例如：转出 A 额度 80，转出 B 额度 50，而期初余额仅 100）。
    *   由于 `transfer_to` 执行时会做 `actual = min(amount * k, source.value)` 的截断。
    *   先执行 A 还是先执行 B，会导致最终两笔转账的实际到账额截然不同。
*   **修正契约**：明确声明：“多笔 `transfer_to` 冲突时，严格按照 Action 提交/加载的顺序（或 Action ID 升序）串行执行，前者的扣减结果实时作为后者的 `source.value` 输入”。

## 2. r8 修改项真的闭账了吗？§6.6 样例够不够当契约测试？

### ① 核心新引入矛盾：Cost 与 `transfer_to` 的「双重扣款与资金蒸发」
在 r8 返工收口中，引入了一个严重的数学漏洞：
*   **现象**：假设 action A 是“补饷 50 两”，其 `Cost` 申报为 50 两，其 effect 为 `{op: transfer_to, source: 省库库银, target: 军饷欠, amount: 50}`。
*   **计算过程**（假设 $k=1$）：
    1.  在 ⓪ 步骤，引擎计算 `省库库银_post = Stock_start - Cost = Stock_start - 50`。**（第一次扣款，50 两直接消失送入 Cost 汇）**
    2.  同样在 ⓪ 步骤，引擎执行 `transfer_to`，从 `省库库银` 转账 50 两到 `军饷欠`。**（第二次扣款）**
    3.  如果 `Stock_start` 刚好是 50 两，在第 1 步扣完后余额已为 0。第 2 步的 `transfer_to` 会因为 `source.value == 0`，导致 `actual = min(50, 0) = 0`。
    4.  **结果**：省库扣了 50 两，但军饷欠款账户收到了 0 两，50 两凭空消失。
*   **闭账方案**：
    *   必须明确：**`Cost`（银）只代表行政/政策执行的额外摩擦成本**。
    *   所有账户间的资金转移（如拨付、补饷）**只能**通过 `transfer_to` 表达，其划转金额**绝不能**计入该 action 的 `Cost` 属性中，否则必然导致双重扣减。
    *   或者，将 `Cost` 的定义改为：该 action 造成的**一切**省库库银流出（包括行政成本和转账金额）。计算 $k$ 时，$\sum Cost$ 代表所有这些流出的总和，但在扣减时，只通过 effects 执行扣减，不进行独立的 `省库库银_post = Stock_start - Σ(k * Cost)` 计算。

### ② §6.6 golden-tick 样例的合同效力评估
*   **评估**：**目前仅是“测试大纲”，无法直接作为契约测试。**
*   **原因**：它缺少具体的**数值边界与断言输入输出**。两位开发者即使算法写错（例如双重扣款），由于没有具体的测试用例数值对账，依然无法在编译期/测试期发现分叉。
*   **优化建议**：在 §6.6 中补充一组**有确定输入输出的 Golden 案例数据**（见下文补充）。

## 3. 还有没有逼回来改架构的隐藏问题？

有以下两个隐藏风险，若不提前锁定，后续写引擎时必会动摇底层 Schema：

1.  **拨付 net/gross 与中饱的越界风险**：
    *   由于 `拨付net/gross` 是外部注入，一旦外部输入了不合规的数据（例如 `gross < net`），会导致 `中饱C = gross - net` 算出负数（相当于中饱私囊的官吏反向贴钱给国库，不合史实与常理）。
    *   **架构防线**：引擎必须在 ⑩ 注入处增加断言拦截：`assert gross >= net`，且 `中饱C = gross - net >= 0`。
2.  **漂没率（运输损耗）的动态表达缺位**：
    *   ⑨ 步骤中 `起运池 = 起运到京 + 漂没C`，但未说明“漂没率”如何计算。
    *   **架构防线**：漂没率必须是一个受环境（如流寇、兵灾 modifier）影响的 Flow 变量，公式应明确为：`漂没C = 起运池 * 漂没率`，`起运到京 = 起运池 * (1 - 漂没率)`。

### 附：推荐补入的 §6.6 Golden-Tick 契约测试用例（数据对账单）

为了让引擎实现者有一致的单元测试，建议锁定如下测试用例：

#### 样例 1：极限财政下的 k 缩减与 transfer 截断
*   **期初状态**：
    *   `省库库银` (Stock_start) = 10.0 万两。
    *   `军饷欠` (B_1) = 100.0 万两。
*   **本期动作**：
    *   Action 1：行政改革，`Cost` = 5.0，无 effect。
    *   Action 2：紧急补饷，`Cost` = 15.0，无 effect；附带 effect：`transfer_to(省库库银, 军饷欠, amount=10.0, efficiency=1.0)`。
*   **外部注入**：本期所有税收、拨付均为 0。
*   **期待计算过程**：
    1.  $\sum Cost = 5.0 + 15.0 = 20.0$。
    2.  由于 $20.0 > 10.0$，$k = 10.0 / 20.0 = 0.5$。
    3.  Action 1 实际扣除库银：$5.0 \times 0.5 = 2.5$。
    4.  Action 2 实际扣除库银：$15.0 \times 0.5 = 7.5$。
    5.  此时库银余额为 $10.0 - 2.5 - 7.5 = 0.0$。
    6.  Action 2 的 `transfer` 额度缩减为 $10.0 \times 0.5 = 5.0$。
    7.  执行 `transfer_to`：因源账户（库银）已为 0，`actual = min(5.0, 0.0) = 0.0`。
*   **期末断言**：
    *   `省库库银` = 0.0 万两。
    *   `军饷欠` (B_1) = 100.0 万两（未得到任何偿还）。
    *   **（此样例成功证明了 k 缩减逻辑、0 余额截断逻辑以及无资金凭空产生）**
